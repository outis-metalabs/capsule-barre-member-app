Member App · proposal · 9 Oct 2026

The owner stops typing bookings.

A phone app for Capsule Barre members that uses aicc-center as the system of record. Members create their own bookings, cancel in time, move a class, join a waitlist, say they've arrived, read their pass, and ask the studio — through the same services the desk already uses.

The phone never calculates money, remaining sessions, refunds, or attendance. A session is spent only when the studio marks the class attended.

What exists today, and what doesn't

Reused untouched

  • Booking rules: capacity, duplicates, eligibility on the class date, weekly quota, auto-confirm
  • Waitlist join and ordered promotion with the same eligibility
  • Cancel-deadline math; move as one operation carrying makeup
  • Deduction only on ATTENDED, from instructor confirmation
  • Pass balances, holds, expiry cron; member phone and consents
  • Visit-only check-in table; owner task list; SMS with opt-out; idempotency; rate limits
  • The enums ReservationSource.MEMBER and CancelActor.MEMBER — defined, never set

Missing

  • Any member identity: no login, token, guard or OTP for members
  • Member actor wiring — create hardcodes DESK, cancel hardcodes STORE
  • Store scope that doesn't come from a staff user
  • Member notifications and push (existing ones are staff Web Push)
  • A per-reformer seat, arrival-window settings, a waitlist offer
  • Member requests, opaque ids, an assistant endpoint
  • An extend-expiry operation — expiry moves only by releasing a hold
  • Anything that tells a new member the app exists

Rules that shaped them

  • Four tabs, three taps max from any tab, no dead ends
  • Time is the hero; values outweigh labels; copy is short and never lectures
  • One accent: red for the single primary action; outline secondary; green for state; ink only for selection. In a destructive sheet the safe choice is the primary
  • No disabled button parked in the thumb zone; "I'm here" exists only in its window
  • The remaining-session meter never moves on a member action

Accepted by two independent UX/UI testers, two passes each; every finding fixed and re-verified.

Security proofs (e2e, mapped to the BA's A-checks)

  1. A member token on any /v1/store/* route → 401; a staff token on /v1/member/* → 401
  2. Studio A's token cannot read studio B's rows, including after switch
  3. storeId, memberId, canceledBy, remainingRestored, status in any member body → 400
  4. Cancel after the deadline → 400 and the row is unchanged; no deduction
  5. Same idempotency key twice → one reservation
  6. Activate with an unregistered phone → 404, no account row
  7. Presence outside the window → 400, no row; inside → one row, attendance untouched
  8. remainingSessions is identical before and after every member write in the suite; it changes only in the existing class-confirmation specs

Gaps and their resolutions

Server

  • G1 No extend operation → add it, with audit
  • G2 Desk phone fix after activation breaks the link → "Relink app account"
  • G3 / G4 Anonymise or end leaves a live account → revoke, drop the studio
  • G16 Nothing tells a new member the app exists → invite SMS at issue
  • G11 / G15 Refund, void, "which pass" mean nothing to the member → display status and per-class projection

Desk process

  • G6 Duplicate phone → reuse the existing row
  • G8 Lost phone → relink after identity check
  • G10 SMS and push both fire → one channel per event
  • G5 Children on a parent's phone → desk books them until a guardian link exists

App copy

  • G9 PERIOD passes → window + frequency, not a count
  • G13 Hold refused by bookings → a plain sentence in the reply
  • G17 Trial runs out → route to Ask

Policy

  • G7 The code always sends · G14 hold limits enforced or unmentioned · G12 bookings on a transferred pass stay; on a voided or refunded pass are cancelled with a notice
